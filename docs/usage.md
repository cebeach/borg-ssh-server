# Introduction

The image is hosted on [docker hub](https://hub.docker.com/repository/docker/chadly314/borg-ssh-server).

Exposes BorgBackup as a single-purpose service (borg serve) over SSH.
See [borgbackup](https://borgbackup.readthedocs.io/en/stable/index.html) to learn more about borg, and, in particular, [hosting repositories](https://borgbackup.readthedocs.io/en/stable/deployment/hosting-repositories.html).

This container has a single user account named borg, runs sshd as PID 1 with logs on stderr, accepts only public-key auth, and requires a bind-mounted persistent repository directory /repos.

The following bind mounts are required to run this container:
- `/repos`: the borgbackup repository root directory
- `/etc/ssh/ssh_host_ed25519_key` and `/etc/ssh/ssh_host_ed25519_key.pub` ED25519 host keys generated by [ssh-keygen](https://manpages.debian.org/bookworm/openssh-client/ssh-keygen.1.en.html)
- `/home/borg/.ssh/authorized_keys`: authorized_keys file which restricts command usage; see `config/authorized_keys_template`
- `/etc/localtime`: While not strictly necessary, helpful for ensuring timezone handling in the container matches that on the host. By inspection on my Synology Diskstation, it appears that DSM is using zoneinfo, so this maps to `/etc/localtime` on DSM.

An entrypoint script is used to coerce the borg account's UID and GID to match those of the bind-mounted /home/borg/.ssh/authorized_keys prior to sshd startup. Please follow best practices for authorized_keys permissions as discussed in OpenSSH [sshd man page](https://manpages.debian.org/bookworm/openssh-server/sshd.8.en.html).

# Metadata (start here)

All of the helper scripts depend on metadata in `scripts/config.sh`.
- BORGBACKUP_VERSION: borgbackup version number we install
- DEBIAN_CODENAME: debian release codename used to select the base image; either 'bookworm' or 'trixie'
- DOCKER_ACCOUNT: Docker hub account name used for image publication
- IMAGE_NAME: base name of the generated image (borg-ssh); the complete name of the image generated by `docker build` in `scripts/build.sh` is \${IMAGE_NAME}:\${DEBIAN_CODENAME}
- IMAGE_REVISION: Integer revision number suffix added to TAG to differentiate incremental updates to the generated image
- TAG: tag assigned to the image using `docker tag` in `scripts/build.sh`: \${BORGBACKUP_VERSION}-\${DEBIAN_CODENAME}-r\${IMAGE_REVISION}. For example, '1.4.3-bookworm-r1'
- FROM: An associative array whose keys are debian codenames and values are the docker hardened image name for that release


# Building the Image

To build the image, run `scripts/build.sh`; this calls `docker build` and `docker tag`

# Removing the Image

To remove the image and remove the build cache, run `scripts/clean.sh`; this calls `docker compose down` to shut down the running container, followed by `docker rmi` and then `docker builder prune` to remove cached layers.


# Starting the Container 

The production target for this image is Docker on a Synology Diskstation, but my build environment is a debian 12 workstation. These instructions pertain only to the build environment to facilitate development and debug iterations. I develop the image and run the container on a debian 12 workstation to confirm gross functionality prior to publictaion to docker hub and pull on the Diskstation.

**To start the container, run `scripts/start.sh`.**

This does some housekeeping first to scrub depenencies prior to container start:
- ensure data/repos and data/ssh exist
- build the ssh host key if necessary
- enforce key permissions
- whine if data/ssh/authorized_keys doesn't exist

If all of the preconditions are met, it then launches the container using `docker compose -f compose/compose.common.yml -f compose/compose.dev.yml up -d`


## host ssh keypair generation for testing

`scripts/start.sh` automates generation of ed25519 keypair for the host at data/ssh/ssh_host_ed25519_key and data/ssh/host_ed25519_key.pub. These files are bind mounted in the docker compose file (below).

This keypair is just for test and validation of the container on the development machine. You'll need to explicitly generate a keypair on your target host machine; e.g. my 'production' host is a Synology Diskstation.

## client ed25519 keypair

You'll need ed25519 keypair on your client machine. Following a 'separation of concerns' approach, I use a keypair explicitly for talking to borg, e.g.:

    $ cd ~/.ssh
    $ ssh-keygen -t ed25519 -f id_ed25519_borg_diskstation


## ssh authorized_keys for testing

You'll need to manually author data/ssh/authorized_keys; this is bind mounted by docker compose as well (below).

The authorized_keys file must follow this syntax exactly:

    command="/home/borg/.local/bin/borg serve --restrict-to-path /repos",no-port-forwarding,no-X11-forwarding,no-agent-forwarding ssh-ed25519 your_public_key your_comment

This restricts the ssh client to running only `/home/borg/.local/bin/borg serve --restrict-to-path /repos",no-port-forwarding,no-X11-forwarding,no-agent-forwarding` as described in [borg serve](https://borgbackup.readthedocs.io/en/stable/usage/serve.html)


## docker compose

`compose/compose.dev.yml` is minimal:

    services:
      borgbackup:
        container_name: borgbackup-server

        ports:
          - "127.0.0.1:2242:22"

        volumes:
          - ../data/repos:/repos:rw
          - ../data/ssh/ssh_host_ed25519_key:/etc/ssh/ssh_host_ed25519_key:ro
          - ../data/ssh/ssh_host_ed25519_key.pub:/etc/ssh/ssh_host_ed25519_key.pub:ro
          - ../data/ssh/authorized_keys:/home/borg/.ssh/authorized_keys:ro
          - /etc/localtime:/etc/localtime:ro

# Verify Authentication and borg Functionality

After starting the container with docker compose (scripts/start.sh), we want to ensure gross functionality as a gate to pushing the image to docker hub.

## ~/.ssh/config

I create an entry in my `~/.ssh/config` to both simplify the URL passed to borg and to incorporate the recommendations for ServerAliveInterval and ServerAliveCountMax discussed in [borg serve](https://borgbackup.readthedocs.io/en/stable/usage/serve.html):

Host localhost.borg
    HostName localhost
    User borg
    Port 2242
    IdentityFile ~/.ssh/id_ed25519_borg_diskstation
    IdentitiesOnly yes
    ServerAliveInterval 10
    ServerAliveCountMax 30

## Attempt to initialize a repo to confirm communication

Use `borg init` to validate both authentication and gross functionality by attempting to initialize a new repo. In this example I'm using --encryption=none just to check functionality; never do this for an actual repo.

# Starting the Container on Synology Diskstation
Start the container on DSM using Synology's Docker GUI, and map all of the bind mounts manually. One everything is set up, save the configuration as a .json file to faciliate automatic population of bind mounts if/when the image is updated. An example version of the .json generated on Diskstation is included as `docs/borg-ssh-server.syno.json`.

## bind mounts using docker on Synology DSM
One caveat: bind mounts on diskstation can only be made relative to DSM shared folders. For example, I have a shared folder named borgbackup on DSM. Using the Synology docker UI to create the bind mount, the path on the host appears as /borgbackup. On my diskstation, the borgbackup shared folder lives in the 'volume2' volume. The absolute path to the borgbackup shared folder is /volume2/borgbackup, but the docker UI exposes this as /borgbackup.

## /etc/localtime bind mount on Synology DSM
Docker on Synology can only 'see' shared folders; it has no visibility on the DSM filesystem. This means it does not have visibility on /etc/localtime. As a workaround, on the diskstation, copy /etc/localtime into the root directory of the borgbackup shared folder. Then create a bind mount from /etc/localtime to /borgbackup/localtime.
